Como esta armado por dentro

Johnny: esto es la parte tecnica. No te hace falta para operar el sitio, el Manual alcanza. Esta aca para que exista, para que si algun dia trabaja otra persona en el sitio no tenga que reconstruir todo desde cero, y para poder repetir el mismo sitio en otro proyecto.

La decision de no usar frameworks no fue estetica: en este hosting no se puede instalar nada. Lo que hay es PHP, MySQL y un administrador de archivos.

Los limites del hosting, y que significan

LimiteConsecuencia
Sin consolaCada cambio es un archivo subido a mano. No hay automatizacion posible
Sin instalador de paquetesCero dependencias externas. Todo escrito a mano
Sin tareas programadasNada corre solo de noche. Todo pasa cuando alguien entra
El envio de mail fallaLas consultas se leen en el panel, no por correo
Por no tener consola, cada archivo lleva un numero de version escrito adentro. Es la unica forma de confirmar que hay realmente en el servidor. Se mira con Ctrl+U en el navegador.

Que pasa cuando alguien entra

RECORRIDO
pedido del navegador
  |
  .htaccess          redirige a https, fija los limites de subida
  |
  pagina.php
    |
    config.php       arranca la sesion, abre la base, captura ?ref=
    antispam.php     solo donde hay formularios
    |
    consulta a MySQL
    |
    nav + contenido + pie

config.php corre primero en cada pagina y hace cuatro cosas antes de que salga un solo caracter: arranca la sesion, captura de donde vino el visitante, abre la conexion y define las constantes del sitio. El orden importa, y esa es la razon del bug mas grave que tuvo el sitio.

Las tablas no comparten la misma configuracion de texto: las viejas usan una y las nuevas otra. Comparar texto entre una y otra da error. Es la razon de un script que fallo y hubo que reescribir.

Como funciona un formulario

Todos escriben en la misma tabla, consultas, y pasan por el mismo filtro en este orden:

FILTRO
cuerpo descartado por tamano  -> avisa que es el tamano, no la sesion
campo trampa lleno            -> finge exito, no guarda nada
token de seguridad invalido   -> "la sesion expiro"
IP bloqueada                  -> falla sin dar detalles
mas de 5 envios por hora      -> pide esperar
mail temporal o inexistente   -> rechaza
  -> guarda la consulta y registra el evento
Cada control falla abierto: si la tabla de registro no existe, el control se saltea y la consulta se guarda igual. Un registro roto nunca puede bloquear una reserva de verdad.

El campo trampa es un campo invisible que un humano nunca completa. Si viene lleno, es un bot: el sitio responde que todo salio bien y no guarda nada, para que el bot no aprenda a esquivarlo.

El visor

Espacios, agenda y la landing usan el mismo patron:

  1. PHP mete todos los datos en la pagina de una vez
  2. Las tarjetas son links reales
  3. El JavaScript intercepta el clic y arma el visor con esos datos
  4. Si el JavaScript falla, el link funciona igual

No hay llamadas al servidor al abrir una tarjeta: todo ya esta en la pagina, por eso abre instantaneo. Lo unico que viaja al servidor es el formulario y el registro del click.

El correo al panel

Una pagina web no puede recibir correo. Solo puede leer correo que ya fue entregado en algun lado.

RECORRIDO
mail entrante
  -> servidor de correo
  -> filtro de cPanel
       accion 1: dejar copia en la casilla   (para webmail)
       accion 2: pasar a pipe_correo.php
  -> el script lee el mensaje y lo guarda en la base
  -> el panel lo muestra en Inbox
El script siempre termina diciendo que todo salio bien, incluso si fallo. Si dijera que fallo, el servidor devolveria el mail al remitente con un error, y un cliente veria un rebote. Los errores se anotan en un archivo aparte.

Los adjuntos se cuentan pero no se guardan. Escribir archivos que manda cualquier desconocido es lo mas peligroso que podria hacer este sistema, y a proposito no lo hace.

ref y boton: dos cosas distintas

Es lo unico del proyecto que conviene entender antes de tocar nada.

EJEMPLO
Entra por el link de Instagram
  ?ref=instagram          -> queda marcado: instagram

Abre el Salon Principal
  evento: abrir_espacio     ref=instagram   boton=(ninguno)

Completa el formulario
  evento: consulta_ok       ref=instagram   boton=lr
  consulta guardada         ref=instagram   boton=lr

Se lee asi: lo trajo Instagram, lo convirtio el formulario.
Si los dos campos se pisaran, todas las reservas quedarian acreditadas al boton y los canales reales mostrarian clicks con cero conversiones para siempre. El unico numero que vale la pena se volveria ilegible. Por eso son dos columnas separadas y no una.

Como se sube un cambio

RUTINA
1. Editar el archivo
2. Revisar que la sintaxis sea valida
3. Subir por cPanel File Manager
4. Ctrl+U en la pagina y confirmar el numero de version
5. Correr el chequeo automatico
6. Guardar el cambio en el repositorio

El repositorio en GitHub es historial y respaldo, no un destino de publicacion. Subir ahi no cambia nada en el sitio.

Hay un script que revisa el sitio en vivo: que todas las paginas respondan, que las versiones publicadas sean las correctas, que el panel no se vea sin sesion y que no haya quedado ningun archivo de prueba expuesto.

Las trampas conocidas

Todas estas costaron horas. Estan anotadas para no volver a perderlas.

SintomaCausa real
Todos los formularios decian "la sesion expiro"La sesion arrancaba despues de que la pagina ya habia empezado a salir, asi que la cookie nunca se enviaba
Pagina en blanco con error 500Error de escritura en el codigo. Pasa antes de que se puedan mostrar errores
"Sesion expirada" al subir un videoEl archivo supero el limite y el servidor descarto todo el envio, incluido el token
Un panel no se podia scrollearUn detalle de como funcionan las grillas en CSS
Texto pegado a la izquierdaUn bloque que ocupa todo el ancho no se puede centrar
El correo no llegaba al panelLa ruta del script estaba escrita de forma relativa y el servidor no la resolvia
Las subidas dejaron de funcionar solasEl hosting saco una pieza de PHP sin avisar
La trampa mas cara de todas: armar un archivo nuevo sobre una copia vieja. Paso tres veces en este proyecto y las tres borro funcionalidad en silencio, sin que nada diera error.

Clonar el sitio para otro proyecto

Todo lo que es especificamente de La Reserva esta en cuatro lugares. Cambiando esos cuatro, el resto sirve para cualquier predio, estudio o centro que publique una agenda y reciba consultas.

#QueDonde
1Identidad: nombre, dominio, mail, WhatsApp, Instagram, coordenadasincludes/config.php
2Colores y tipografiaLas variables al principio de css/style.css
3Contenido: espacios, retiros, fotos, textosTodo en la base de datos
4Vocabulario: "retiros" y "espacios"Buscar y reemplazar en el texto visible

Lo que no hay que tocar al clonar

  • El sistema anti spam: funciona igual para cualquier sitio
  • El sistema de usuarios y sesiones
  • El modelo de ref y boton
  • La estructura de las tablas de consultas, eventos y referidos
Un clon completo, con contenido cargado, es un dia de trabajo. Lo que lo hace posible es que nada de La Reserva esta escrito a mano fuera de esos cuatro lugares, y conviene que siga asi.
